# Ramag 性能报告

本文记录 Ramag 三个核心工作台的性能设计、测试方法、实测结果与已知边界。目标不是给出脱离场景的“跑分”，而是回答三个实际问题：

1. 日常操作是否能即时响应？
2. 数据量增大后，延迟和内存是否仍然有界？
3. 当前最值得继续优化的路径是什么？

## 结论先行

| 模块 | 日常路径 | 大数据表现 | 当前主要边界 |
|---|---|---|---|
| VCS（试验性） | 当前仓库完整刷新 18.454 ms；单路径状态 13.702 ms | 10 万文件 UI 状态补丁合并 67.791 μs；10 万提交图布局 3.284 ms | Git 子进程本身仍受磁盘、仓库结构和 Hook 影响 |
| 数据库 | MySQL / PostgreSQL 全库导出约 11 万行/秒；MongoDB 导出约 7.1 万文档/秒 | Redis 完整保真导出 46,014 Key / 161,017 条目需 26.126 s | Redis 全库迁移需要逐 Key 读取类型、TTL 和完整值，往返次数最多 |
| 剪贴板 | 百万历史下最近 500 条读取 5.513 ms；文本入库约 5.195 ms | UI 最坏本地过滤 1.918 ms；4K 缩略图 58.603 ms且在后台执行 | 百万历史罕见词或无命中全文搜索约 12.5 s |

总体判断：VCS 与剪贴板常用交互已达到桌面应用的即时响应水平，SQL / MongoDB 全量导出吞吐稳定在每秒 7 万至 11 万条。当前优先级最高的性能问题不是渲染，而是剪贴板加密历史的深度全文搜索；其次是 Redis 全库保真迁移的网络往返成本。

数据库运行于本机 Docker，连接走 `127.0.0.1`。因此数据库结果主要反映 Ramag 的分页、类型转换、序列化和文件写入效率，不代表远程网络下的绝对耗时。

### 统计口径

- VCS 和剪贴板微基准均先预热，再报告中位数；重要路径同时记录 P95。
- 数据库导入导出使用完整种子数据执行单轮端到端测试，包含数据库读取、类型转换、序列化和本地文件 IO。
- 编译和 Release 链接时间不计入性能结果。
- 合成数据用于验证算法随规模增长的趋势，不用于推算真实用户磁盘占用。
- 本报告没有测量窗口动画、GPU 合成或远程数据库 RTT，因此不把函数级耗时直接等同于最终点击延迟。

## VCS 性能（试验性功能）

VCS 当前仍处于试验阶段。以下数据用于说明现有实现的性能特征和扩展边界，不代表功能稳定性或兼容性承诺。

### 设计目标

VCS 的关键目标不是让一次全量 `git status` 跑得更快，而是避免普通文件保存触发全仓库工作。当前刷新链路为：

```text
文件事件 → 60 ms 合并窗口 → 路径级 status → 有序补丁合并 → 只刷新受影响标签
```

Git 查询在固定 worker 中运行，UI 线程只处理有界结果。仓库元数据变化才刷新分支和全局状态；普通文件变化优先走路径级查询。

### 当前仓库：真实 Git 操作

测试仓库为 Ramag，预热后 50 轮。工作区当时包含少量脚本改动，测试路径为 `scripts/build-windows-local.sh`。

| 操作 | 中位数 | P95 |
|---|---:|---:|
| 工作区完整刷新（状态 + 分支并发） | 18.454 ms | 23.817 ms |
| 全量状态 | 17.925 ms | 24.234 ms |
| 本地与远程分支合并读取 | 13.121 ms | 15.855 ms |
| 最近 100 条历史 | 15.228 ms | 21.066 ms |
| 最近 1,000 条历史 | 15.992 ms | 19.187 ms |
| 单路径状态 | 13.702 ms | 16.424 ms |
| 四条 Git 命令并发的富状态对照 | 16.528 ms | 22.113 ms |
| 标准上下文 Diff | 13.660 ms | 17.580 ms |
| 整文件上下文 Diff | 13.534 ms | 18.756 ms |
| 全量 Project Files | 16.250 ms | 22.042 ms |
| 单路径 Project Files | 12.605 ms | 16.527 ms |

把 60 ms 文件事件合并窗口与单路径状态中位数相加，普通保存从最后一个文件事件到状态结果约为 73.7 ms。它是链路估算，不包含操作系统调度和最后一帧绘制。

### 大型合成 UI 数据

| 场景 | 数据规模 | 中位数 |
|---|---:|---:|
| Project Files 单路径成员合并 | 100,000 文件 | 0.792 μs |
| 工作区状态补丁合并 | 100,000 条状态 | 67.791 μs |
| Project Files 折叠树构造 | 100,000 文件 | 2.071 ms |
| Project Files 全展开 | 100,001 可见行 | 6.203 ms |
| 提交图布局 | 100,000 次提交 | 3.284 ms |
| Diff 虚拟化布局 | 110,000 行 | 3.595 ms |
| 超大 Diff 语法高亮门控 | 110,000 行 | 0.519 ms |
| Unified Diff 解析 | 100,000 逻辑行 / 2.84 MB | 4.940 ms |

超大 Diff 会主动跳过完整语法树构建，但仍保留行级虚拟化展示。这比“所有输入都强行高亮”更稳定：大文件不会把一次打开操作放大成长期内存占用。

### 既有大型仓库基线

此前在 Apple M2 Pro 上记录过更偏 Git 后端的压力结果，可用于观察算法差异，不与本轮硬件数字直接比较：

- 100,000 条文件状态：路径查询 17.735 ms，全量状态 503.434 ms。
- 连续读取 20 × 1,000 条提交：持久流 116.124 ms，重复 `--skip` 为 877.853 ms。

这两组数据说明路径级刷新和持久日志流不是微优化，而是分别避免了全仓库扫描和深分页重复工作。

## 数据库性能

### 数据集

测试使用项目自带的四数据库专用 Docker 环境，运行前重新生成并校验数据：

| 引擎 | 数据规模 | 额外覆盖 |
|---|---:|---|
| MySQL 8.0 | 100,005 行 | JSON、二进制、百万字节字段、空间类型 |
| PostgreSQL 17 | `public` 100,004 行，另有 8,000 条分析数据 | JSONB、数组、范围、网络、位串、XML 等原生类型 |
| Redis 7 | 46,014 Key / 161,017 条目 | String、Hash、List、Set、ZSet、Stream、TTL、大集合 |
| MongoDB 8.2 | 125,102 文档 | 混合 `_id`、Extended JSON、大文档、索引与聚合 |

### Release 端到端导入导出

| 操作 | 数据量 | 文件大小 | 耗时 | 约合吞吐 |
|---|---:|---:|---:|---:|
| MySQL 全库导出 | 100,005 行 | 32.5 MiB | 871 ms | 114,800 行/s |
| PostgreSQL `public` 导出 | 100,004 行 | 35.1 MiB | 884 ms | 113,100 行/s |
| MongoDB 全库导出 | 125,102 文档 | 56.5 MiB | 1,761 ms | 71,000 文档/s |
| MongoDB 全库导入 | 125,102 文档 | 56.5 MiB | 2,371 ms | 52,800 文档/s |
| Redis DB 0 导出 | 46,014 Key / 161,017 条目 | 14.8 MiB | 26,126 ms | 1,761 Key/s |
| Redis 导入 DB 14 | 46,014 Key | 14.8 MiB | 23,507 ms | 1,957 Key/s |

SQL 导出使用每页 1,000 行的 keyset 分页，有主键时不会随着页码变深而重复跳过前面的记录；生成的 INSERT 以最多 500 行或约 1 MiB 为一批。MongoDB 使用 `_id` keyset，每页 2,000 文档，导入按最多 500 文档或 8 MiB 分批。

Redis 数字明显更低，但工作量也不同：它需要遍历整个 Keyspace，并为每个 Key 读取类型、剩余 TTL 和完整值；大集合还要按 4,096 条分页，二进制值需要转 hex 保真。当前 SCAN 批次已是 5,000，瓶颈主要来自逐 Key/逐页往返，而不是 JSONL 文件写入。

### 交互路径的资源边界

Ramag 不会默认把整个远端数据库装进 UI 内存：

- MySQL / PostgreSQL 的分页查询由服务端执行，查询结果另有 256 MiB 客户端硬上限。驱动保留可选的自动 `LIMIT` 能力，但当前界面不默认启用。
- SQL 元数据最多保留 50,000 项且结果预算为 32 MiB；MongoDB 元数据最多保留 50,000 项。
- MongoDB 单次查询最多保留 50,000 文档或 32 MiB BSON。
- Redis Keyspace 使用游标 SCAN；大集合支持继续加载，单页最多 5,000 条。
- SQL、Redis、MongoDB 使用彼此独立的 Tokio runtime，某一类数据库的慢查询不会直接占满另一类数据库的执行线程。

这些限制的目标是稳定性：面对异常大结果，应用会截断并提示缩小范围，而不是持续增长内存直到界面或系统失去响应。

### 验证状态

四个数据库驱动的 139 个单元与真实集成测试全部通过。独立 Release 性能探针通过。

完整工作区数据库流程另发现两个与性能无关的环境问题：MySQL 固定测试用户只有 `ramag_test` 权限，而两个应用层导入测试会创建并删除 `ramag_e2e_sql`、`ramag_e2e_jsonl`，因此被 MySQL 拒绝。报告中的只读导出路径和四驱动门禁不受影响，但这两个权限失败不能记作完整工作区全绿。

## 剪贴板性能

### 设计目标

剪贴板需要同时满足低空闲开销、快速唤起和长期历史加密。当前实现把三类工作分开：

- 空闲时每 400 ms 只读取系统剪贴板修改计数，内容未变化就不做解密或磁盘访问。
- 最近 500 条以 `Arc` 形式保留在已解密缓存中，唤起和刷新只复制引用。
- 完整历史保存在 redb 中，整条记录经 AES-256-GCM 加密；时间、内容指纹和 UUID 反查使用独立索引。

### 加密历史库

合成文本负载约 220 字节。10 万条和 100 万条分别构建加密记录与三张索引；最近读取 20 轮、最近命中搜索 10 轮、全量搜索分别 5 轮和 3 轮，其余轻量操作 20 至 100 轮。

| 操作 | 100,000 条中位数 | 1,000,000 条中位数 | 1,000,000 条 P95 |
|---|---:|---:|---:|
| 最近 500 条 | 5.581 ms | 5.513 ms | 7.532 ms |
| 最近区域凑满 500 个搜索结果 | 5.517 ms | 5.530 ms | 5.836 ms |
| 搜索命中最后一条 | 1,069.902 ms | 12,529.289 ms | 12,561.112 ms |
| 搜索完全无命中 | 1,070.525 ms | 12,544.664 ms | 12,626.919 ms |
| 内容指纹命中 | 0.011 ms | 0.011 ms | 0.096 ms |
| 正常清理快速检查 | 0.001 ms | 0.001 ms | 0.001 ms |
| 文本保存事务 | 5.299 ms | 5.195 ms | 8.323 ms |

最近读取、去重和正常清理不会随着总历史量明显退化，说明索引设计有效。深度搜索则需要按时间顺序逐条解密、反序列化并匹配正文；历史量增长 10 倍时，无命中搜索从约 1.07 s 增长到约 12.54 s，基本呈线性退化。

测试库逻辑文件大小分别约 257 MiB 和 4 GiB。redb 会按内部策略扩张文件，且合成负载不代表真实内容分布，因此该数字只能说明“百万条历史不是轻量配置”，不能直接当作每条记录的磁盘估算。

### UI、图片与系统剪贴板

| 场景 | 中位数 | P95 | 说明 |
|---|---:|---:|---|
| 500 条缓存，空查询 | 0.0015 ms | 0.0016 ms | 只构造引用结果 |
| 500 条缓存，预览命中 | 0.0136 ms | 0.0144 ms | 预览优先匹配 |
| 500 × 4 KiB 正文前缀，全部未命中 | 1.9177 ms | 2.0847 ms | UI 即时过滤最坏样本 |
| 320×180 PNG 缩略图 | 0.537 ms | 0.683 ms | 不放大 |
| 1920×1080 PNG 缩略图 | 15.129 ms | 15.337 ms | 解码、缩放、重新编码 |
| 3840×2160 PNG 缩略图 | 58.603 ms | 58.816 ms | 在后台 worker 执行 |
| macOS `changeCount` | 0.0006 ms | 0.0008 ms | 空闲轮询的实际系统调用 |
| 读取当前系统剪贴板 | 0.0211 ms | 8.6728 ms | 当前内容类型未记录，避免泄露剪贴板内容 |
| 读取前台应用 | 0.0003 ms | 0.0053 ms | macOS NSWorkspace |

400 ms 采集周期意味着内容变化检测平均等待约 200 ms、最坏接近 400 ms；文本保存本身约 5 ms，因此正常采集的感知延迟主要由轮询周期决定。图片缩略图是 CPU 大头，但已移出 UI 线程。

主视图使用虚拟列表，抽屉最多展示 60 张卡片；图片缓存限制为 96 项、256 MiB 和最多 4 个并发加载。即使快速滚动图片历史，临时任务与解码内存也有明确上限。

### 当前改进方向

百万历史的完整全文搜索是本轮唯一达到秒级的交互路径。推荐分两步处理：

1. 先增加分段或时间预算搜索，例如每批扫描固定数量或约 200 ms，逐步展示结果和搜索进度。优点是改动较小，并能限制单次 worker 占用；代价是较老结果不会一次返回。
2. 如果产品必须支持百万条一次性任意子串搜索，再设计带密钥的 token / n-gram 候选索引，命中候选后解密复核。它能显著降低查询时间，但会增加写入、磁盘和隐私设计复杂度。

当前不建议优先优化空闲轮询、最近缓存、UI 过滤或缩略图路径，因为实测没有显示这些位置存在用户可感知瓶颈。

## 如何复核

VCS 基准已作为默认忽略测试保留：

```bash
RAMAG_PERF_REPO=/path/to/repo \
RAMAG_PERF_PATH=src/main.rs \
RAMAG_PERF_ITERATIONS=50 \
cargo test --release -p ramag-infra-git --test performance \
  reports_workspace_refresh_latency -- --ignored --nocapture

cargo test --release -p ramag-infra-git \
  reports_large_diff_parse_latency -- --ignored --nocapture

cargo test --release -p ramag-tool-vcs \
  reports_large_ -- --ignored --nocapture
```

数据库种子和探针分别位于 [`scripts/db-test`](../scripts/db-test) 与 [`transfer_live.rs`](../crates/ramag-app/tests/transfer_live.rs)。剪贴板本轮使用临时 Release 探针，探针与 4 GiB 临时库在测试后已删除；测试轮数、负载和全部结果已在本文保留。

性能数字会受硬件、文件系统缓存、Git 版本、数据库版本、网络 RTT 和真实数据分布影响。后续对比应使用同一机器、同一 Release 配置和同一数据集，重点观察相对变化与 P95，而不是把本文数字当作所有环境的承诺值。
