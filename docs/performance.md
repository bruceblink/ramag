# Ramag 性能报告

本文记录 Ramag 三个核心工作台的性能设计、测试方法、实测结果与已知边界。目标不是给出脱离场景的“跑分”，而是回答三个实际问题：

1. 日常操作是否能即时响应？
2. 数据量增大后，延迟和内存是否仍然有界？
3. 当前最值得继续优化的路径是什么？

## 结论先行

| 模块 | 日常路径 | 大数据表现 | 当前主要边界 |
|---|---|---|---|
| VCS（试验性） | 当前仓库完整刷新 16.217 ms；单路径状态 11.779 ms | 10 万状态补丁合并 91.917 μs；10 万提交图布局 2.553 ms | Git 子进程仍受磁盘、仓库结构和 Hook 影响 |
| 数据库 | MySQL / PostgreSQL 全库导出约 11 万行/秒；MongoDB 导出约 7.1 万文档/秒 | Redis 保真导出 45,014 Key / 160,017 条目为 1.569 s | Redis 超大集合的后续分页与导入仍受网络往返约束 |
| 剪贴板 | 百万历史下最近 500 个搜索结果 3.966 ms；文本入库 P50 2.993 ms | 百万历史罕见词或无命中搜索约 0.2 s | 低于 3 个 UTF-8 字节的短查询仍走完整加密扫描 |

总体判断：三项原主要瓶颈均已消除。剪贴板百万历史深度搜索从约 12.5 s 降到约 0.2 s，Redis 完整导出从 26.126 s 降到 1.569 s，普通 VCS 保存刷新链路估算从 73.7 ms 降到约 23.8 ms。SQL / MongoDB 全量导出继续稳定在每秒 7 万至 11 万条。

### 统计口径

- VCS 和剪贴板微基准均先预热，再报告中位数；重要路径同时记录 P95。
- 数据库导入导出使用完整种子数据执行单轮端到端测试，包含数据库读取、类型转换、序列化和本地文件 IO。
- 编译和 Release 链接时间不计入性能结果。
- 合成数据用于验证算法随规模增长的趋势，不用于推算真实用户磁盘占用。
- 本报告没有测量窗口动画、GPU 合成或远程数据库 RTT，因此不把函数级耗时直接等同于最终点击延迟。

## VCS 性能（试验性功能）

VCS 当前仍处于试验阶段。以下数据用于说明现有实现的性能特征和扩展边界，不代表功能稳定性或兼容性承诺。

### 设计目标

VCS 的关键目标不是让一次全量 `git status` 跑得更快，而是避免普通文件保存触发全仓库工作。当前刷新链路为：

```text
文件事件 → 12 ms 安静窗口（持续事件最长 40 ms）→ 路径级 status → 有序补丁合并 → 只刷新受影响标签
```

Git 查询在固定 worker 中运行，UI 线程只处理有界结果。仓库元数据变化才刷新分支和全局状态；普通文件变化优先走路径级查询。事件持续到来时使用首事件固定截止时间，避免传统尾缘防抖一直推迟刷新。

### 当前仓库：真实 Git 操作

测试仓库为 Ramag，预热后 50 轮。工作区包含本次性能改动，测试路径为 `Cargo.toml`。

| 操作 | 中位数 | P95 |
|---|---:|---:|
| 工作区完整刷新（状态 + 分支并发） | 16.217 ms | 17.622 ms |
| 全量状态 | 15.395 ms | 17.561 ms |
| 本地与远程分支合并读取 | 11.230 ms | 12.015 ms |
| 最近 100 条历史 | 13.330 ms | 14.949 ms |
| 最近 1,000 条历史 | 13.961 ms | 15.526 ms |
| 单路径状态 | 11.779 ms | 12.654 ms |
| 四条 Git 命令并发的富状态对照 | 14.761 ms | 16.169 ms |
| 标准上下文 Diff | 13.660 ms | 17.580 ms |
| 整文件上下文 Diff | 13.534 ms | 18.756 ms |
| 全量 Project Files | 16.250 ms | 22.042 ms |
| 单路径 Project Files | 12.605 ms | 16.527 ms |

把 12 ms 安静窗口与单路径状态中位数相加，普通保存从最后一个文件事件到状态结果约为 23.8 ms；持续事件流按 40 ms 上限估算约为 51.8 ms。它们是链路估算，不包含操作系统调度和最后一帧绘制。

### 大型合成 UI 数据

| 场景 | 数据规模 | 中位数 |
|---|---:|---:|
| Project Files 单路径成员合并 | 100,000 文件 | 1.167 μs |
| 工作区状态补丁合并 | 100,000 条状态 | 91.917 μs |
| Project Files 折叠树构造 | 100,000 文件 | 2.583 ms |
| Project Files 全展开 | 100,001 可见行 | 7.328 ms |
| 提交图布局 | 100,000 次提交 | 2.553 ms |
| Diff 虚拟化布局 | 110,000 行 | 4.253 ms |
| 超大 Diff 语法高亮门控 | 110,000 行 | 0.605 ms |
| Unified Diff 解析 | 100,000 逻辑行 / 2.84 MB | 4.940 ms |

超大 Diff 会主动跳过完整语法树构建，但仍保留行级虚拟化展示。这比“所有输入都强行高亮”更稳定：大文件不会把一次打开操作放大成长期内存占用。

### 既有大型仓库基线

此前在 Apple M2 Pro 上记录过更偏 Git 后端的压力结果，可用于观察算法差异，不与本轮硬件数字直接比较：

- 100,000 条文件状态：路径查询 17.735 ms，全量状态 503.434 ms。
- 连续读取 20 × 1,000 条提交：持久流 116.124 ms，重复 `--skip` 为 877.853 ms。

这两组数据说明路径级刷新和持久日志流不是微优化，而是分别避免了全仓库扫描和深分页重复工作。

## 数据库性能

### 数据集

测试使用项目自带的四数据库专用 Docker 环境，运行前重新生成并校验数据：

| 引擎 | 数据规模 | 额外覆盖 |
|---|---:|---|
| MySQL 8.0 | 100,005 行 | JSON、二进制、百万字节字段、空间类型 |
| PostgreSQL 17 | `public` 100,004 行，另有 8,000 条分析数据 | JSONB、数组、范围、网络、位串、XML 等原生类型 |
| Redis 7 | 46,014 Key / 161,017 条目 | String、Hash、List、Set、ZSet、Stream、TTL、大集合 |
| MongoDB 8.2 | 125,102 文档 | 混合 `_id`、Extended JSON、大文档、索引与聚合 |

### Release 端到端导入导出

| 操作 | 数据量 | 文件大小 | 耗时 | 约合吞吐 |
|---|---:|---:|---:|---:|
| MySQL 全库导出 | 100,005 行 | 32.5 MiB | 871 ms | 114,800 行/s |
| PostgreSQL `public` 导出 | 100,004 行 | 35.1 MiB | 884 ms | 113,100 行/s |
| MongoDB 全库导出 | 125,102 文档 | 56.5 MiB | 1,761 ms | 71,000 文档/s |
| MongoDB 全库导入 | 125,102 文档 | 56.5 MiB | 2,371 ms | 52,800 文档/s |
| Redis DB 0 导出（优化前） | 46,014 Key / 161,017 条目 | 14.8 MiB | 26,126 ms | 1,761 Key/s |
| Redis DB 0 导出（当前） | 45,014 Key / 160,017 条目 | 14.7 MiB | 1,569 ms | 28,690 Key/s |
| Redis 导入 DB 14（优化前） | 46,014 Key | 14.8 MiB | 23,507 ms | 1,957 Key/s |
| Redis 导入 DB 14（当前复核） | 45,014 Key | 14.7 MiB | 13,794 ms | 3,263 Key/s |

SQL 导出使用每页 1,000 行的 keyset 分页，有主键时不会随着页码变深而重复跳过前面的记录；生成的 INSERT 以最多 500 行或约 1 MiB 为一批。MongoDB 使用 `_id` keyset，每页 2,000 文档，导入按最多 500 文档或 8 MiB 分批。

Redis 仍需遍历整个 Keyspace，并为每个 Key 读取类型、剩余 TTL 和完整值；大集合按 4,096 条分页，二进制值转 hex 保真。优化后 SCAN 仍以 5,000 个 Key 为一批，但每 16 个 Key 的首页通过同一个多路复用连接并发读取，再严格按原 SCAN 顺序写 JSONL；超大集合的后续页继续逐 Key 流式读取，内存与输出顺序不变。

当前复核时，种子中的 1,000 个一小时 TTL Key 已自然过期，因此数据量比旧基线少约 2.2%。该差异不足以解释导出从 26.126 s 到 1.569 s 的约 16.6 倍变化。导入实现未参与本轮优化，当前导入数字只用于证明新导出文件仍可完整恢复，不把差值记作优化收益。

### 交互路径的资源边界

Ramag 不会默认把整个远端数据库装进 UI 内存：

- MySQL / PostgreSQL 的分页查询由服务端执行，查询结果另有 256 MiB 客户端硬上限。驱动保留可选的自动 `LIMIT` 能力，但当前界面不默认启用。
- SQL 元数据最多保留 50,000 项且结果预算为 32 MiB；MongoDB 元数据最多保留 50,000 项。
- MongoDB 单次查询最多保留 50,000 文档或 32 MiB BSON。
- Redis Keyspace 使用游标 SCAN；大集合支持继续加载，单页最多 5,000 条。
- SQL、Redis、MongoDB 使用彼此独立的 Tokio runtime，某一类数据库的慢查询不会直接占满另一类数据库的执行线程。

这些限制的目标是稳定性：面对异常大结果，应用会截断并提示缩小范围，而不是持续增长内存直到界面或系统失去响应。

### 验证状态

此前四个数据库驱动的 139 个单元与真实集成测试全部通过。本次 Redis 并发首页读取的类型、输入顺序、TTL、二进制与缺失 Key 测试通过，Release 导出后再导入 DB 14 的端到端复核通过。

当前真实 Redis 集成套件 15 项中 14 项通过；唯一失败是种子完整性断言仍要求至少 46,000 Key，而上述 1,000 个 TTL Key 已过期，并非驱动或导出结果错误。重新生成专用测试种子后即可恢复该环境断言。

完整工作区数据库流程另发现两个与性能无关的环境问题：MySQL 固定测试用户只有 `ramag_test` 权限，而两个应用层导入测试会创建并删除 `ramag_e2e_sql`、`ramag_e2e_jsonl`，因此被 MySQL 拒绝。报告中的只读导出路径和四驱动门禁不受影响，但这两个权限失败不能记作完整工作区全绿。

## 剪贴板性能

### 设计目标

剪贴板需要同时满足低空闲开销、快速唤起和长期历史加密。当前实现把三类工作分开：

- 空闲时每 400 ms 只读取系统剪贴板修改计数，内容未变化就不做解密或磁盘访问。
- 最近 500 条以 `Arc` 形式保留在已解密缓存中，唤起和刷新只复制引用。
- 完整历史保存在 redb 中，整条记录经 AES-256-GCM 加密；时间、内容指纹和 UUID 反查使用独立索引。
- 深度搜索使用由主密钥派生的带密钥三字节 Bloom 预筛；索引不保存明文，候选仍逐条解密并按原规则复核。

### 加密历史库

合成文本负载约 220 字节。10 万条搜索报告 5 轮中位数，100 万条报告 3 轮中位数；文本保存报告 200 轮的 P50 / P95。

| 操作 | 优化前 | 当前 | 变化 |
|---|---:|---:|---:|
| 100,000 条，无命中搜索 | 1,070.525 ms | 18.459 ms | 约 58.0 倍 |
| 1,000,000 条，命中最老一条 | 12,529.289 ms | 198.691 ms | 约 63.1 倍 |
| 1,000,000 条，完全无命中 | 12,544.664 ms | 219.915 ms | 约 57.0 倍 |
| 1,000,000 条，最近区域凑满 500 个结果 | 5.530 ms | 3.966 ms | 约快 28.3% |
| 文本保存事务 P50 | 5.195 ms | 2.993 ms | 约快 42.4% |
| 文本保存事务 P95 | 8.323 ms | 3.842 ms | 约快 53.8% |
| 百万历史仅超限 1 条的候选定位 | 99.608 ms | 27.250 μs | 约 3,655 倍 |

搜索索引每条使用 256 字节位图，对预览与正文的小写 UTF-8 三字节窗口计算带密钥哈希。位图只负责排除不可能命中的记录，假阳性会进入 AES 解密复核，因此不会改变搜索结果、最近优先顺序、数量限制或正文预算。百万条位图净数据约 244 MiB，实际 redb 占用还包含 B 树页和键。

已有历史在后台分批建立索引；完成前继续使用 2 至 8 线程的加密全扫描，索引数量或顺序不一致时也自动回退。单条可搜索正文超过 1 MiB 时直接写全 1 位图，避免保存时无界计算，同时保证不漏结果。低于 3 个 UTF-8 字节的查询无法形成三字节窗口，仍走原完整扫描路径。

### 当前边界

百万历史的常规深度搜索已进入约 0.2 s 范围。剩余最差情况主要是 1 至 2 个 ASCII 字节的罕见查询、位图饱和的超长正文，以及旧库首次后台建索引期间的完整扫描。继续覆盖极短查询需要额外的一字节 / 二字节索引，会明显增加磁盘与写放大；在缺少真实查询分布前不继续扩大索引。

空闲轮询、最近缓存、UI 过滤和缩略图路径当前均有明确边界，实测未显示新的用户可感知 CPU 瓶颈。

## 如何复核

VCS 基准已作为默认忽略测试保留：

```bash
RAMAG_PERF_REPO=/path/to/repo \
RAMAG_PERF_PATH=src/main.rs \
RAMAG_PERF_ITERATIONS=50 \
cargo test --release -p ramag-infra-git --test performance \
  reports_workspace_refresh_latency -- --ignored --nocapture

cargo test --release -p ramag-infra-git \
  reports_large_diff_parse_latency -- --ignored --nocapture

cargo test --release -p ramag-tool-vcs \
  reports_large_ -- --ignored --nocapture
```

剪贴板基准也作为默认忽略测试保留，临时数据库在测试结束时自动删除：

```bash
RAMAG_PERF_CLIP_ITEMS=1000000 \
RAMAG_PERF_ITERATIONS=3 \
cargo test --release -p ramag-infra-storage \
  reports_large_encrypted_clip_search_latency -- --ignored --nocapture

RAMAG_PERF_ITERATIONS=200 \
cargo test --release -p ramag-infra-storage \
  reports_clip_save_latency -- --ignored --nocapture

RAMAG_PERF_CLIP_ITEMS=1000000 \
cargo test --release -p ramag-infra-storage \
  reports_large_selection_latency -- --ignored --nocapture
```

数据库种子和探针分别位于 [`scripts/db-test`](../scripts/db-test) 与 [`transfer_live.rs`](../crates/ramag-app/tests/transfer_live.rs)。Redis 性能复核使用专用本地 Docker 数据集，导入目标为测试 DB 14，结束后自动清空。

性能数字会受硬件、文件系统缓存、Git 版本、数据库版本、网络 RTT 和真实数据分布影响。后续对比应使用同一机器、同一 Release 配置和同一数据集，重点观察相对变化与 P95，而不是把本文数字当作所有环境的承诺值。
