## 术语表与命名约定

| 规范名称 | English / Acronym | 在本路线图中的职责边界 | 不代表什么 |
|---|---|---|---|
| 数据库查询工具 | Database Client | Ramag 中连接、浏览、查询和编辑数据库的整体产品能力 | 不包含 Git、SSH、对象存储等其他工具 |
| 结果数据编辑器 | Result Data Editor | 展示查询结果、分页、滚动、排序、过滤和数据编辑的界面 | 不代表 SQL 编辑器或数据库表设计器 |
| 查询控制台 | Query Console | 绑定连接与当前 Schema 的 SQL/文档查询会话 | 不代表数据库连接池或后台执行线程 |
| Schema 浏览器 | Schema Explorer | 展示数据库、Schema、表、集合及元数据的对象树 | 不代表数据库元数据缓存本身 |
| 服务端分页 | Server-side Pagination | 通过 `LIMIT/OFFSET`、MongoDB `skip/limit` 等方式只读取当前数据页 | 不代表客户端只隐藏已加载数据 |
| 数据库驱动 | Database Driver | `ramag-domain` 定义的能力接口及 MySQL、PostgreSQL、MongoDB 等具体适配器 | 不强行把 SQL、文档和 Key-Value 能力合并成一个接口 |
| DataGrip-like | DataGrip-like Core Workflow | 参考 DataGrip 的核心数据库浏览、查询、编辑和分析工作流 | 不承诺复制 DataGrip 的全部方言、插件和 IDE 能力 |
| 迁移审批记录 | Migration Approval Record | 记录用户确认的迁移上下文、脚本指纹和数据库执行结果 | 不保存 SQL 正文、连接凭据或替代数据库审计日志 |

## 1. 背景与目标

DataGrip 的参考价值在于完整的数据库工作流，而不是单个 SQL 输入框。官方文档将 Query Console、Database Explorer、数据编辑器和查询结果视图作为相互配合的核心界面：[Query Consoles](https://www.jetbrains.com/help/datagrip/query-consoles.html)、[数据编辑器](https://www.jetbrains.com/help/datagrip/data-editor-and-viewer.html) 和 [用户界面导览](https://www.jetbrains.com/help/datagrip/guided-tour-around-the-user-interface.html)。

Ramag 已经具备多数据库连接、Schema 浏览、查询编辑、结果编辑、导入导出和数据同步等基础能力。本路线图的目标是：

1. 先补齐高频且影响最大的数据库浏览体验，尤其是可见的双轴滚动和可控分页。
2. 建立可扩展的查询会话、事务和查询分析模型，避免继续把能力堆在单个结果面板中。
3. 以 MySQL 和 PostgreSQL 为第一目标，随后分别完善 MongoDB；Redis 保持符合 Key-Value 数据模型的专用交互。
4. 用可验收的阶段目标取代“完全对标 DataGrip”这一不可控的二元目标。

## 3. 产品边界与原则

### 3.1 目标用户工作流

第一目标是开发者和运维人员的高频闭环：

```text
选择连接和 Schema
    -> 打开查询控制台
    -> 编写并执行查询
    -> 在结果数据编辑器中分页、滚动、筛选和编辑
    -> 查看影响范围或执行计划
    -> 提交、回滚或导出结果
```

### 3.2 设计原则

1. **先保证可见性，再追求密度**：结果列不能覆盖，双轴滚动条和当前页状态必须可发现。
2. **默认安全**：默认分页读取有限数据；写入操作明确显示影响行数，并提供提交/回滚边界。
3. **服务端优先**：分页、排序和过滤尽量下推数据库，客户端只处理当前窗口数据。
4. **按数据模型分层**：SQL、文档和 Key-Value 驱动分别演进，不为表面统一而引入大量 `NotImplemented`。
5. **能力逐步增强**：先交付稳定的文本和表格能力，再逐步增加结构化计划、图形和对比功能。
6. **可验证交付**：每个里程碑都必须有单元/集成测试、`git diff --check` 和真实窗口截图或等价 UI 验证。

## 4. 分阶段开发计划

### M1：结果数据编辑器（优先级 P0）

目标：让数据库表和查询结果可以稳定地浏览大量行和大量列。

功能清单：

- 默认 `pageSize=100`。
- 提供 `200`、`500`、`1000` 预设值，以及自定义正整数输入。
- SQL 和 MongoDB 使用各自驱动语义执行服务端分页；用户切换 page size 时回到第 1 页并清理旧页状态。
- 同时提供可见的垂直和水平滚动条；底部分页状态栏不能遮挡最后一行。
- 保留虚拟列表，避免因为降低 page size 而退化为一次性渲染全量结果。
- 保留列宽估算和手动调整；宽列必须能滚动到完整内容。
- 为分页状态、哨兵行、页大小边界和结果表双轴滚动增加回归测试。

验收标准：

1. 查询超过 100 行时，首屏只请求并展示当前页，界面显示“第 1 页”，可以进入下一页。
2. 在 `100/200/500/1000` 和自定义 page size 间切换时，查询结果、页码和状态栏保持一致。
3. 行数超过视口高度时，可以拖动垂直滚动条；列总宽超过视口时，可以拖动水平滚动条。
4. 真实 Windows 窗口截图能确认滚动条、最后一行、分页控件和结果列没有重叠。
5. SQL、MongoDB 的既有分页安全检查、显式 `LIMIT/OFFSET` 行为和写查询行为不回归。

实现边界：

- 页大小选择器和分页状态属于结果数据编辑器，不放入全局设置第一版。
- 首版只允许有限范围的自定义值，例如 `1..=10000`；超出范围时在输入处提示，不发送请求。
- 暂不为任意 SQL 自动改写带有显式分页、锁定、写入或多语句的查询。

### M2：查询控制台与结果会话（优先级 P1）

目标：让一次数据库连接下的多个查询会话可独立工作，接近 DataGrip 的 Query Console 体验。

功能清单：

- 一个连接下支持多个查询控制台，每个控制台绑定连接和当前 Schema。
- 查询编辑器、执行状态、取消操作、错误信息和结果页签互不覆盖。
- 查询历史和草稿按连接/控制台恢复，切换页签不丢失未提交文本。
- 支持结果标签页保留、关闭和重新打开；长查询执行期间允许切换到其他控制台。
- 记录当前连接、Schema、执行耗时、影响行数和分页状态。

#### M2-A：SQL 查询上下文隔离（已落地切片）

实现范围：

- 查询和 COUNT 请求分别使用代次；连接、Schema 或 SQL 改变后，旧回包不能覆盖当前控制台状态。
- 普通查询和 EXPLAIN 查询绑定各自的结果目标；取消查询只清理发起请求的面板，保留另一面板的结果与分页状态。
- 服务端取消确认使用取消代次；用户已经切换到新查询时，旧请求的取消提示不会污染当前通知区域。
- 连接、Schema 或 SQL 改变时先读取旧连接的取消句柄，再替换上下文配置；取消失败只写日志，不覆盖当前查询的错误或结果。
- Docker 实测 MySQL 8.0 `SELECT SLEEP(30)` 与 PostgreSQL 17 `SELECT pg_sleep(30)` 均可通过后端 ID 取消，并在限定时间内结束。
- 关闭连接标签或将连接配置标记为失效时，先让旧查询标签失效并发出取消，再释放连接池；用户草稿仍由连接级恢复逻辑保留。

验收标准：

1. 取消数据查询会清理数据面板，取消执行计划不会清理已有数据结果或页码。
2. 连接、Schema 或 SQL 切换后，旧查询结果、COUNT 结果和取消提示都不能写入新上下文。
3. 多标签并行执行、连接断开和真实 MySQL/PostgreSQL 环境验证仍需补充。

#### M2-B：最近关闭查询草稿恢复（已落地切片）

实现范围：

- 关闭包含用户手写 SQL 的查询标签时，将标题、SQL 文本和当前 Schema 放入当前连接的有限恢复栈。
- 查询标签栏提供“重新打开最近关闭的查询”按钮，按后进先出恢复，最多保留 10 条草稿。
- 只恢复编辑器草稿，不恢复结果集、正在执行的任务、分页状态或未提交事务；切换连接时清空恢复栈。

验收标准：

1. 关闭手写 SQL 标签后可以重新打开，标题、SQL 文本和 Schema 与关闭前一致。
2. 连续关闭超过 10 条时只保留最近 10 条，恢复顺序为后关闭的优先。
3. 没有手写草稿的自动浏览标签不会污染恢复栈；连接切换后旧连接草稿不能被恢复。
4. 恢复标签重新接入草稿自动保存和查询标签上限控制，单元测试和真实窗口截图通过。

架构要求：

- 在 `ramag-tool-dbclient` 中明确“查询控制台状态”和“结果数据编辑器状态”的所有权。
- 在 `ramag-domain`/`ramag-app` 中只抽象跨驱动都成立的会话语义；连接池、取消句柄等基础设施细节留在具体驱动。
- 查询执行任务必须保留代次或会话标识，旧请求完成后不能覆盖新控制台的结果。

#### M2-A：查询上下文与在途回包隔离（已落地切片）

设计目标：查询控制台中的 SQL 文本、连接、Schema 和表上下文变化时，旧的在途查询与 COUNT 回包不能再写入当前结果面板。结果内存活跃状态也必须跟随当前可见结果视图切换，避免后台标签长期占用活跃预算。

实现边界：

- 使用查询代次和 COUNT 代次隔离旧异步任务；上下文变化会停止客户端等待并清理 `Running` 状态，但不假设服务端取消一定成功。
- 已完成的数据结果在编辑 SQL 时可以保留；只有正在执行的结果会清空，避免显示“执行中”假状态。
- SQL、MongoDB 的查询语义和连接驱动接口不因此强行统一；本切片只收紧 SQL 查询控制台状态边界。

验收标准：

1. 查询执行期间编辑 SQL、切换连接、Schema 或表上下文，旧结果/错误不能覆盖当前控制台，旧 COUNT 也不能恢复分页状态。
2. 两个查询标签切换后，结果内存活跃标记只保留当前可见标签及其当前结果视图。
3. 查询取消、正常完成和上下文失效后，工具栏执行状态与结果面板状态一致。

验收标准：

- 两个控制台可以同时绑定同一连接并分别执行查询，结果不会串页或串状态。
- 关闭并重新打开工作区后，已保存草稿和最近查询可以恢复。
- 查询取消、连接断开和切换 Schema 时，不会把旧错误写入当前控制台。

### M3：事务与安全编辑（优先级 P1）

目标：为可编辑结果提供明确、可控、可恢复的写入流程。

功能清单：

- 自动提交/手动提交模式。
- 提交、回滚、当前事务状态和未提交变更提示。
- 编辑、删除、新增前显示关键列、影响范围和风险提示。
- 批量修改失败时显示成功/失败明细，不隐藏数据库返回的错误。
- 根据驱动能力显示事务控制；MongoDB、Redis 不强行复用 SQL 事务 UI。

#### M3-A：SQL 手动事务提交与回滚（已落地切片）

实现范围：

- MySQL 和 PostgreSQL 驱动提供独立的事务会话句柄；事务连接在提交或回滚前保持租用，避免后续语句落到其他连接。
- 查询控制台提供“开始事务”“提交”“回滚”和未提交状态提示；结果表的编辑、删除和新增复用当前事务会话。
- 手动事务内拒绝嵌套 `BEGIN`、`COMMIT`、`ROLLBACK` 等控制语句；事务切换连接、Schema 或关闭查询标签时自动回滚。
- 真实 MySQL/PostgreSQL 集成测试覆盖事务内读取、回滚不落库和提交落库；测试表使用显式数据库方言标识，避免依赖隐含 Schema 搜索路径。

验收证据：

- `cargo test -p ramag-infra-mysql --test integration`：13 个测试通过（含 `manual_transaction_commit_and_rollback`）。
- `cargo test -p ramag-infra-postgres --test integration`：15 个测试通过（含 `manual_transaction_commit_and_rollback`）。
- 手动事务控制的真实窗口截图仍需补充；本切片不宣称已经完成原生 Windows UI 截图验收。

#### M3-B：事务失败状态与恢复提示（已落地切片）

实现范围：

- 事务内 SQL、行内编辑、删除和新增失败时，查询控制台记录最近一次错误，并显示“事务异常”和“请回滚或重试”状态；数据库事务不会因普通语句失败被 UI 擅自回滚。
- 提交或回滚失败时清理已经结束或失效的事务句柄，保留持久错误提示，并显示“事务已结束，请重新开启”，避免误报提交成功。
- 下一次成功开启事务会清理旧错误；切换连接、Schema 或关闭标签时清理旧状态并继续执行已有的自动回滚逻辑。

验收证据：

- `cargo test -p ramag-tool-dbclient --lib` 覆盖自动提交、事务异常和事务处理中状态优先级。
- 真实 MySQL/PostgreSQL 事务提交、回滚和事务内读取由 M3-A 集成测试继续覆盖。
- 原生窗口截图仍需在 Windows computer-use 环境补充；本切片不宣称已经完成截图验收。

架构要求：

- 为 SQL 驱动增加最小事务能力接口和隔离级别能力声明，避免在通用 `Driver` 中塞入所有后端专属语义。
- 将提交/回滚状态纳入查询控制台生命周期，而不是仅存在于结果表组件。
- 所有写操作继续复用现有安全检查、确认和可取消机制。

验收标准：

- 手动提交模式下，编辑后关闭控制台会提示未提交变更。
- 回滚后重新查询，数据与数据库一致；提交后能显示影响行数。
- 连接断开或事务失效时，UI 明确显示状态，不允许误报提交成功。

#### M3-C：SQL 事务保存点（已落地切片）

实现范围：

- MySQL 和 PostgreSQL 的手动事务支持创建、回滚到最近保存点和释放最近保存点；保存点操作不会结束外层事务。
- 查询控制台最多保留 32 个由应用生成的保存点名称，工具栏显示“保存点”“回滚最近”“释放最近”按钮和最近保存点名称。
- 保存点名称只允许 ASCII 字母、数字和下划线，且必须以字母开头；事务内普通 SQL 仍拒绝直接执行保存点及其他事务控制语句。
- 回滚到保存点后恢复该保存点创建时的未提交状态；释放保存点时同步移除该保存点及其后续嵌套保存点。切换连接、Schema 或关闭标签时，保存点随外层事务一起回滚并清理。

验收证据：

- 共享 SQL 层对保存点名称边界、SQL 片段和超长输入有单元测试。
- `cargo check` 覆盖 `ramag-infra-sql-shared`、`ramag-app` 和 `ramag-tool-dbclient` 的保存点接口连通性。
- 真实 MySQL/PostgreSQL 保存点回滚和释放仍需在带数据库的集成环境补充；原生窗口截图仍需在 Windows computer-use 环境补充。

### M4：查询分析与 Schema 协作（优先级 P2）

目标：补齐高级数据库开发辅助能力，但不阻塞核心查询流程。

#### M4-A：独立执行计划结果视图（已落地）

实现范围：

- 生成 EXPLAIN 时写入独立的执行计划结果面板，不替换数据结果面板中的内容。

#### M4-B：只读 Schema Diagram 元数据预览（已落地切片）

实现边界：

#### M4-C：字段结构差异预览（已落地切片）

设计目标：在现有表设计器的写操作确认前，补充基于字段元数据的结构差异视图，让用户同时看到将执行的 SQL 和字段增删/修改内容；差异预览本身只读，不改变已有执行安全检查。

实现边界：

- 差异来自原始 `Column` 与当前字段草稿，不解析 UI 文本，也不把差异文本直接发送到数据库。
- 同名字段按大小写不敏感方式匹配；修改显示为删除行加新增行，新增和删除显示为对应的 `+`/`-` 行。
- 预览支持分别复制生成的 SQL 和字段差异文本；编辑任意字段后清理旧预览，确认执行时仍重新生成 SQL。
- 当前切片只覆盖列名、类型、NULL 属性、默认值和注释；索引、外键和表改名仍属于后续范围，表级跨表对比由 M4-D 提供。

验收标准：

1. 修改表字段并点击预览后，同时显示 SQL 预览和字段结构差异，未变更字段保留上下文行。
2. 新增、删除、类型或属性修改能生成稳定的增删行；字段名大小写变化不会被误判为同一字段修改。
3. 复制按钮得到的文本与当前预览一致；继续编辑后不能执行旧预览内容。
4. 差异计算、大小写匹配和换行压缩有单元测试，`cargo test -p ramag-tool-dbclient --lib` 通过。

#### M4-D：同连接表结构对比（已落地切片）

设计目标：在 Schema 浏览器的表右键菜单中选择源表和目标表，读取两张 SQL 表的真实元数据并生成只读差异视图；目标表可以位于当前连接的另一个 Schema，帮助用户在不执行 DDL 的前提下检查结构漂移。

实现边界：

- M4-D 仅支持 MySQL 和 PostgreSQL 的同一连接；目标表名不带 Schema 时使用源表所在 Schema，也可以输入 `schema.table` 进行跨 Schema 对比。跨连接对比由后续 M4-F 扩展，MongoDB、Redis 和迁移脚本不在本切片范围内。
- 差异来源为驱动返回的 `Column`、`Index` 和 `ForeignKey`，不解析 UI 文本，也不执行任何迁移 SQL。
- 同名对象按大小写不敏感方式匹配；定义变化显示为删除旧定义和新增新定义，索引列顺序与外键引用列顺序保留。
- 对话框提供复制差异、刷新元数据以及水平/垂直滚动；单类元数据读取失败时保留其他结果并显示按源表/目标表区分的警告，同时在标题中显示两侧完整的 Schema 和表名。
- 后台读取带请求代次和连接、源 Schema、目标 Schema、源表名、目标表名校验，旧响应不能覆盖当前对比上下文。

验收标准：

1. 表右键菜单可以打开结构对比，输入目标表名或 `schema.table` 后显示列、索引和外键三组差异。
2. 真实 MySQL 和 PostgreSQL 表的新增、删除、修改列以及索引/外键变化可以被正确识别；不产生 DDL 或数据写入。
3. 失败的单类元数据读取不会清空其他类别；刷新后滚动位置回到起点，旧异步响应不会覆盖新结果。
4. 差异文本可以复制，窗口内容超出可视区域时可通过两条滚动条访问完整定义。
5. `cargo test -p ramag-tool-dbclient --lib`、两套 SQL 驱动集成测试和真实窗口截图均通过。

#### M4-E：查询结果数据网格差异比较（已落地切片）

设计目标：在查询控制台中保存一次已加载结果作为基准，重新执行查询后比较字段和行变化，帮助开发者检查数据变化；比较只读，不执行额外的数据库写操作。

实现边界：

- 结果工具栏提供保存基准、比较当前结果和清除基准三个操作；基准使用结果数据快照，不保存一份重复的 SQL 文本。

#### M4-H：表结构迁移 SQL 预览（已落地切片）

设计目标：在 M4-D/M4-F 的表结构对比结果上生成“目标表调整为源表结构”的迁移 SQL，帮助开发者审阅和保存跨环境 DDL；本切片只生成脚本，不自动执行数据库写操作。

实现边界：

- 仅支持 MySQL 和 PostgreSQL，目标连接的驱动必须与源连接一致；脚本包含 Schema、表、字段、索引和外键的安全标识符引用。
- 生成顺序固定为先删除受影响的外键和索引，再处理字段增删改，最后补回索引和外键，避免字段变化被现有依赖阻塞。
- 字段新增、删除、类型/NULL/默认值/注释变化，索引新增、删除、属性或字段变化，以及外键新增、删除和引用变化都会进入脚本；删除和修改语句会在预览顶部单独计数提醒。
- 通过复制按钮复制完整脚本，通过保存按钮使用 `.sql` 文件保存；保存使用现有原子写入流程，取消保存不会产生文件。

- `cargo test -p ramag-tool-dbclient schema_migration` 覆盖 MySQL 依赖重建顺序、PostgreSQL 引用标识符和注释转义、无差异结果与不安全类型拒绝。

- 真实 MySQL/PostgreSQL 数据库执行回放已由 M4-I 的 Docker 集成测试补充；不同版本方言差异和真实窗口截图仍需补充。本切片仍不把生成成功视为数据库执行成功。

#### M4-I：表结构迁移执行与回读（已落地切片）

设计目标：在 M4-H 生成的迁移 SQL 上增加受控的目标库执行入口，让用户在对比窗口内完成“复核、确认、执行、重新读取元数据”的闭环；本切片不改变保存脚本默认不执行的行为。

实现边界：

- 执行按钮只出现在迁移预览面板；脚本会在弹出确认前重新从当前完整元数据生成，并在确认回调中再次校验请求代次、表上下文和脚本文本，预览变化时拒绝执行。
- 目标连接标记为生产环境时保持只读，只能预览或保存；空迁移不会发送数据库请求；执行期间禁止刷新、切换预览和重复保存/执行。
- PostgreSQL 使用 `Query::transactional` 将整批 DDL 放入一个事务，失败时回滚；MySQL 保持 DDL 的自动提交语义，并在确认提示和生成警告中说明失败后可能部分变更。
- 执行成功后重新读取源表和目标表的列、索引和外键，执行失败只显示错误，不覆盖当前已加载的差异内容；所有执行结果写入结构化日志。

验收证据：

- `cargo test -p ramag-tool-dbclient` 覆盖迁移查询的 MySQL/PostgreSQL 事务选择及现有脚本生成安全检查。
- `crates/ramag-infra-mysql/tests/migration_replay.rs` 和 `crates/ramag-infra-postgres/tests/migration_replay.rs` 覆盖 Docker 数据库中的成功回放；PostgreSQL 额外验证失败迁移不会留下部分结构。
- `cargo check -p ramag-tool-dbclient --all-targets`、数据库驱动集成测试、格式检查、`git diff --check` 和源码尺寸检查通过；真实窗口截图仍需补充。

#### M4-J：外键动作元数据与迁移保真度（已落地切片）

设计目标：补齐 MySQL 和 PostgreSQL 外键的 `ON DELETE`/`ON UPDATE` 元数据，使结构差异和迁移脚本不再把已有约束动作静默降级为数据库默认行为。

实现边界：

- `ForeignKeyAction` 使用跨驱动的规范枚举表示 `NO ACTION`、`RESTRICT`、`CASCADE`、`SET NULL` 和 `SET DEFAULT`；旧的外键序列化记录缺少动作字段时兼容为 `NO ACTION`。
- MySQL 从 `INFORMATION_SCHEMA.REFERENTIAL_CONSTRAINTS` 读取动作，PostgreSQL 从 `pg_constraint` 的更新/删除动作码读取动作；无法识别的数据库值直接返回元数据错误。
- 表结构差异和 Schema 树显示两类动作；迁移生成器把非默认动作写入 `ON DELETE`/`ON UPDATE` 子句，并把动作变化视为外键定义变化。
- 本切片不改变 M4-I 的生产连接只读、显式确认、PostgreSQL 事务和 MySQL 部分变更提示；M4-M 对生成列重建、IDENTITY 切换和 PostgreSQL 列顺序变化仍会保留人工复核提示。

验收证据：

- `cargo test -p ramag-domain` 覆盖动作名称解析、规范 SQL 输出和未知值拒绝。
- `cargo test -p ramag-tool-dbclient --lib` 覆盖动作差异文本、动作变化触发的外键重建和迁移 SQL 输出。
- MySQL/PostgreSQL Docker 集成测试覆盖真实 `CASCADE` 元数据读取以及迁移回放后的动作回读；格式检查、差异检查和源码尺寸检查继续执行。
- 真实 Windows 窗口截图仍需补充；本切片不将代码测试视为原生窗口验收。

#### M4-K：迁移审批记录（已落地切片）

设计目标：为 M4-I 的“复核、确认、执行、回读”流程保留本地可回看的迁移审批记录，使用户能确认哪一次脚本在何时针对哪个目标表执行，以及执行是否成功。

实现边界：

- 用户在确认对话框中接受当前脚本后立即创建记录，记录源/目标连接与表、数据库驱动、语句数量、破坏性语句数量、审批时间和 SQL SHA-256 指纹。
- 迁移成功时记录执行耗时和数据库警告数量；迁移失败时记录有界错误摘要；执行中断或应用关闭时保留“已确认”状态，避免把未完成操作误标记为成功。
- 记录保存在现有本地偏好存储中，最多保留最近 50 条并限制 JSON 大小；加载时去重、校验指纹和文本边界。SQL 正文、密码和其他连接凭据不进入审批记录。
- 迁移预览面板展示最近 5 条记录及状态、目标表、时间、脚本指纹、语句计数和结果摘要；生产连接仍不可执行，也不会生成审批记录。

验收证据：

- `cargo test -p ramag-tool-dbclient --lib schema_diff_dialog` 覆盖脚本指纹稳定性、记录去重/数量上限、偏好大小上限和非法指纹拒绝。
- `cargo check -p ramag-tool-dbclient --all-targets`、`cargo fmt --all -- --check`、`git diff --check` 和源码尺寸检查通过。
- 启动桌面程序并打开表结构迁移预览，检查迁移工具栏、审批记录区域、长文本滚动和生产连接按钮状态；真实数据库执行仍使用 M4-I 的 Docker 回放证据。

#### M4-L：查询结果差异单元格定位（已落地切片）

设计目标：在两侧结果按主键或唯一键匹配成功的变更行中，进一步指出具体变化的列、基准/当前行列位置以及旧值和新值，帮助用户直接定位数据差异。

实现边界：

- 继续使用现有的字段匹配和稳定键行匹配；只有稳定键匹配到的变更行生成单元格差异。没有共同稳定键时继续按整行新增/删除展示，不把不可靠的行配对显示成单元格修改。
- 内部位置使用零基索引，界面和复制文本使用从 1 开始的行号、列号；列名同时展示，列顺序变化仍由字段差异区域单独说明。
- 每次比较最多保留 `2000` 个单元格差异详情，超出部分只计数并在界面和复制文本中提示；单元格值沿用现有预览长度，避免复制和渲染超大字段。
- 单元格定位只读取两侧已经加载的结果快照，不重新访问数据库，不执行写操作；刷新和异步比较仍沿用现有请求代次保护。

验收条件：

1. 稳定键匹配的变更行显示每个变化单元格的基准/当前位置、列名、旧值和新值，复制文本包含相同信息。
2. 没有共同稳定键时保留整行新增/删除语义，单元格定位区域不伪造匹配结果。
3. 超过 `2000` 个变化单元格时，比较结果保持有界，界面和复制文本报告省略数量。
4. `cargo test -p ramag-tool-dbclient --lib result_diff`、格式检查、`git diff --check`、源码尺寸检查和文档检查通过；真实 Windows 窗口截图仍需补充。

#### M4-M：列元数据保真度（已落地切片）

设计目标：让表结构对比和迁移预览读取并保留数据库列的真实顺序、生成规则和自增规则，减少脚本生成后再人工补写列属性的情况。

实现边界：

- `Column` 增加可兼容旧记录的列序号、MySQL `AUTO_INCREMENT`、生成列表达式、`VIRTUAL`/`STORED` 存储方式和 PostgreSQL `IDENTITY` 模式；旧 JSON 缺少这些字段时按未提供处理，不凭空推断数据库行为。
- MySQL 从 `information_schema.COLUMNS` 读取 `ORDINAL_POSITION`、`EXTRA` 和 `GENERATION_EXPRESSION`；新增或修改列时生成 `FIRST`/`AFTER`、`AUTO_INCREMENT` 及 `GENERATED ALWAYS AS (...) VIRTUAL/STORED`。
- PostgreSQL 读取列序号、`IDENTITY` 模式和生成列表达式；迁移生成器支持新增、删除和切换 `IDENTITY`，生成列表达式变化通过删除并重建目标列处理，并明确提示该操作可能丢失现有值。
- PostgreSQL 不生成伪造的列重排 SQL；检测到已有列顺序变化时只显示人工复核提示。生成列表达式、默认值和类型继续使用现有 SQL 片段安全检查。
- Schema 差异文本同时显示 `POSITION`、`AUTO_INCREMENT`、`IDENTITY` 和生成列表达式；元数据读取失败或属性不完整时返回错误或显示明确警告。

验收条件：

1. MySQL 集成测试验证列序号、`AUTO_INCREMENT`、`VIRTUAL` 和 `STORED` 及其表达式读取；PostgreSQL 集成测试验证 `ALWAYS`、`BY DEFAULT`、`STORED` 和表达式读取。
2. 迁移单元测试验证 MySQL `FIRST`/`AFTER`、自增和生成列 SQL，PostgreSQL `IDENTITY` SQL、生成列重建和列顺序提示。
3. `cargo test -p ramag-tool-dbclient --lib schema_migration`、`cargo test -p ramag-infra-mysql --test column_metadata`、`cargo test -p ramag-infra-postgres --test column_metadata`、格式检查、`git diff --check` 和源码尺寸检查通过；集成测试缺少 `RAMAG_TEST_*` 环境变量时会跳过，不能替代真实数据库执行证据。
4. 桌面程序打开表结构对比和迁移预览时，差异文本能显示列序号与生成属性；真实 Windows 窗口截图仍需补充。

#### M4-N：服务端分页精确页码跳转（已落地切片）

设计目标：利用 SQL 分页后台 COUNT 的精确结果，让用户可以直接打开已知范围内的结果页，同时不把未知总数或 MongoDB 查询变成无边界的深分页请求。

实现边界：

- SQL 结果总数为 `Known` 时，跳页输入使用从 1 开始的页码，并严格限制在 `1..=total_pages`；请求仍通过现有 `LIMIT/OFFSET` 边界和算术检查。
- COUNT 尚未完成或失败时，SQL 只接受上一页、下一页；下一页仍由哨兵行确认，不能因为页码输入绕过结果边界。
- MongoDB 不执行精确总数查询，继续使用已加载页偏移，只允许返回已加载页或加载下一页；本切片不为 MongoDB 添加虚假的末页信息。

验收条件：

1. 已知总数 `250`、页大小 `100` 时可接受第 2、3 页，拒绝第 4 页和当前页重复请求。
2. 总数未知时只接受相邻页，跳过未加载页的请求被拒绝。
3. 页码输入去除首尾空白后转为内部从 0 开始的索引；非整数、0、超出总页数和平台无法表示的页码返回错误，不发送数据库请求。
4. `cargo test -p ramag-tool-dbclient --lib`、格式检查、`git diff --check` 和源码尺寸检查通过；真实窗口截图仍需在可附着的 Windows computer-use 会话中补充。

#### M4-O：表树表大小状态（已落地切片）

设计目标：借鉴 DBeaver 对象导航树的统计信息展示，在表名右侧显示数据库返回的物理存储大小，帮助用户在浏览对象时快速识别大表；该信息属于元数据状态，不触发额外的数据扫描。

实现边界：

- MySQL 使用 `DATA_LENGTH + INDEX_LENGTH`；PostgreSQL 使用 `pg_total_relation_size`，包含表数据、索引和 TOAST 存储。
- 普通视图和物化视图不显示表大小；驱动无法返回统计时保留为空，不使用估算值填充。
- 表名区域允许收缩并显示省略号，大小状态固定在行尾；大小使用统一的字节、KiB、MiB、GiB 格式化规则。
- Schema 首次展开时随表列表一起读取大小；刷新 Schema 会重新读取，避免把旧统计长时间留在界面中。
- 统计信息只进入表树和本地元数据模型，不写入迁移 SQL，不参与表结构差异判断。

验收条件：

1. MySQL 和 PostgreSQL 的普通表在真实元数据回包中带有 `size_bytes`；视图与物化视图保持为空。
2. 表树能在长表名被截断时继续显示右侧大小，缺少大小时不留下空白占位。
3. 旧的本地表记录缺少 `size_bytes` 时仍能反序列化，刷新后使用新的统计值。
4. `cargo test -p ramag-domain`、`cargo test -p ramag-tool-dbclient --lib`、MySQL/PostgreSQL 集成测试、格式检查、`git diff --check` 和源码尺寸检查通过；真实 Windows 窗口截图仍需补充。

功能清单：

- EXPLAIN 结果支持原始文本和常见格式的结构化树，后续再评估图形化执行计划。DataGrip 将 Query Plan 作为独立结果页，并支持树、原始计划、图形和火焰图展示，可作为交互参考：[Query Execution Plan](https://www.jetbrains.com/help/datagrip/query-execution-plan.html)。
- 基于现有表、列、索引和外键元数据生成 Schema Diagram。
- 表结构和 DDL diff，已落地表设计器字段级差异预览、同连接或跨连接的表级列/索引/外键对比，以及带显式确认、外键动作保留、执行后回读和本地审批记录的迁移 SQL 工作流；后续再评估更细的方言适配。
- 查询结果数据网格已支持基准快照、基础差异比较、同类型 SQL 连接之间的只读结果比较和稳定键匹配下的单元格差异定位；表结构已支持同类型 SQL 连接之间的只读对比和包含列属性保真的迁移工作流，后续继续扩展更细的方言适配。DataGrip 的数据编辑器也提供网格对比能力，可作为交互参考：[Explore data in the data editor](https://www.jetbrains.com/help/datagrip/explore-data-in-data-editor.html)。
- 为 MySQL/PostgreSQL 增加更精确的方言检查、对象导航和补全；MongoDB 单独设计文档查询辅助。

验收标准：

- EXPLAIN 不影响原查询结果；计划执行失败时保留原始数据库错误。
- Schema Diagram 的节点和边全部来自已加载元数据，不凭 UI 推断关系。
- DDL diff 必须可预览、可复制；迁移 SQL 可保存但不自动执行，应用内执行必须经过人工复核、目标连接生产只读检查和显式确认。

## 5. 架构落地顺序

1. **结果数据编辑器状态**：先抽出统一的 `PageSize`、页状态和边界校验，SQL/MongoDB 通过各自分页器接入。
2. **UI 滚动和分页控件**：在 SQL 和 MongoDB 结果表分别挂载纵向、横向滚动句柄，并复用统一的视觉规范。
3. **应用层查询会话**：为控制台建立独立的执行代次、结果集合和取消状态。
4. **驱动能力声明**：事务、结构化计划等能力按 SQL、文档、Key-Value 分组扩展，不修改无关驱动。
5. **元数据协作能力**：复用现有 Schema、Column、Index、ForeignKey 和 DDL 模型，先做只读预览，再增加执行。

禁止的捷径：

- 不把所有查询结果一次性加载到客户端来“解决”滚动问题。
- 不把默认 page size 仅改成较小常量而不提供用户选择和分页状态重置。
- 不在 `ramag-domain::Driver` 中加入每个数据库都无法实现的统一大接口。
- 不以“支持 DataGrip 全部功能”作为单个 PR 的验收标准。

## 6. 分支、提交与 PR 策略

本路线图对应多个独立交付，不创建一个长期承载全部功能的“大分支”。每个里程碑从最新 `origin/main` 建立独立分支，并在验证通过后立即提交和推送。

### M1 建议拆分

建议分支名：`codex/feat/result-editor-pagination`

建议提交顺序：

1. `fix: keep database result vertical scrolling usable`
2. `feat: add configurable database result page size`
3. `test: cover database result pagination controls`

如果滚动条修复已经在独立 PR 中完成，M1 新分支只包含分页大小、状态重置、SQL/MongoDB 接入和对应测试，避免重复修改已合并或待合并的滚动条代码。

建议 PR 主题：

> feat: improve database result editor pagination

PR 内容应说明：默认页大小、可选页大小、服务端分页边界、SQL/MongoDB 差异、回归测试和真实窗口截图证据。

## 8. 风险、验收条件与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| 多数据库方言差异 | 自动分页、排序、事务和 EXPLAIN 语义不一致 | 先按驱动能力声明和方言适配器拆分 |
| 大结果集内存和 UI 性能 | 查询结果卡顿或占用过多内存 | 服务端分页、虚拟列表、页大小上限和取消机制并存 |
| 结果编辑的主键/并发问题 | 误更新或覆盖他人修改 | 明确身份列、生成条件更新、提交前确认并保留错误明细 |
| 图形化能力投入过大 | 延误核心查询体验 | M4 只读预览，先交付原始/结构化文本 |
| 长期分支漂移 | 难以合并和回滚 | 每个里程碑独立分支、单一功能提交 |

进入下一阶段前需要满足：

1. 上一阶段的验收标准和测试条件全部通过。
2. 没有已知的分页、滚动、查询取消或数据写入回归。
3. 明确该阶段对应的驱动范围，不把未实现的驱动能力伪装成通用能力。
4. PR 描述包含功能边界、验证命令和截图/集成环境限制。

## 9. 结论

Ramag 应该采用 **“以 DataGrip 为交互参考、以核心工作流为产品边界、以里程碑逐步扩大能力”** 的策略。M1 结果数据编辑器已经完成默认 100 条分页、可选 page size 和可靠的双轴滚动；M3-A 已完成 SQL 手动事务的提交/回滚驱动链路和真实 MySQL/PostgreSQL 验证，M3-B 已补齐事务失败状态和恢复提示，后续继续补充原生窗口截图、更细的会话语义和结构化执行计划。

## 10. DBeaver 与 DataGrip 对标后的后续计划

本计划以当前 `codex/feat/datagrip-like-development` 的已落地能力为起点，不追求复制某个产品的全部功能。DBeaver 的 Database Navigator 把连接、Schema、表和对象操作集中在可筛选的导航树中，并可在导航树中显示表统计信息；DataGrip 的 Database Explorer、数据编辑器、Query Plan 和 Schema Comparison 分别覆盖对象导航、结果查看、执行计划和结构迁移工作流。这些公开交互可以作为 Ramag 的参考：[DBeaver Database Navigator](https://dbeaver.com/docs/dbeaver/Database-Navigator/)、[DataGrip Database Explorer](https://www.jetbrains.com/help/datagrip/database-explorer.html)、[DataGrip data editor](https://www.jetbrains.com/help/datagrip/data-editor-and-viewer.html)、[DataGrip Query Execution Plan](https://www.jetbrains.com/help/datagrip/query-execution-plan.html)、[DataGrip schema comparison and migration](https://www.jetbrains.com/help/datagrip/schema-comparison-and-migration.html)。

### 10.1 当前基线

当前版本已经具备以下基础：

- 表树已显示 MySQL 和 PostgreSQL 普通表的大小状态，视图不显示虚假的统计值；大小设置、刷新和长表名截断已有基础实现。
- SQL 结果支持服务端分页、页大小切换、精确页码跳转、排序、筛选和全局水平滚动开关；结果表支持稳定键约束下的单元格编辑。
- 查询标签已有独立执行代次、取消、最近关闭草稿恢复、查询历史和事务提交/回滚/保存点能力。
- 已有执行计划结果、表结构和查询结果差异比较、跨连接比较、迁移 SQL 预览、人工确认、执行后回读和本地审批记录。
- 表树支持按当前连接隔离的表收藏和最近访问筛选；筛选模式会按需加载有记录的 Schema，并在完整刷新后清理已不存在的对象记录。
- SQL 编辑器可以按选中文本或光标所在的表引用定位到表树；定位会保持连接和 Schema 信息，必要时加载目标 Schema 并高亮实际表名。

后续工作应优先补齐这些能力之间的连续操作路径：**导航树定位对象 -> 打开查询或设计器 -> 执行并查看结果 -> 编辑或比较 -> 预览并确认迁移**。

### 10.2 P0：结果工作区与对象导航

目标是先让高频的“找表、查数据、看大字段、修改一行”流程稳定且容易发现，建议作为接下来 1 至 2 个迭代完成。

1. **结果查看模式与大字段查看器**

   - 在现有数据网格上补充表格、树形、文本和转置视图；模式切换只改变已加载结果的展示方式，不重新发送查询。
   - 单元格支持 NULL、空字符串、二进制和超长文本的明确状态；大字段在独立查看区域中按需读取或分段展示，不能因为打开查看器而一次性复制整个结果集。
   - 提供复制为文本、CSV、JSON 和 SQL 值的动作，并保留当前筛选、排序和选中单元格上下文。

2. **编辑状态与提交反馈**

   - 在现有回车提交基础上增加未提交单元格状态、批量提交/撤销和失败后保留编辑内容的路径；默认仍要求行定位键和安全的条件更新。
   - 事务打开时显示当前会话状态；提交、回滚、刷新和切换标签之间互相阻塞，避免用户误以为数据已经写入。
   - 更新成功后只刷新受影响行或当前页，更新失败显示数据库错误、影响行数和可重试动作，不静默覆盖用户输入。

3. **表树统计与对象导航**

   - 保留当前表大小显示，增加加载中、未知、读取失败和统计过期状态；刷新统计时不阻塞已经显示的表名。
   - 在表、列和查询编辑器之间建立稳定的定位动作：从表树打开数据/DDL，从 SQL 中选中表引用或把光标放在表名上后定位到导航树，并显示当前 Schema 和连接。当前 SQL 表定位入口已落地。
   - 表树支持对象过滤、收藏、按类型分组和最近访问；所有过滤都在本地完成，元数据读取仍使用分页或批量请求。

4. **查询标签与结果服务区**

   - 查询标签显示执行耗时、返回行数、结果状态和取消状态；同一标签的多个结果页不能被后一次执行覆盖。
   - 查询历史、最近关闭草稿和当前结果之间保留连接、Schema、方言和执行时间上下文；切换连接后禁止回放到错误的目标。
   - 为上述场景补充真实窗口检查：长表名和长列名、超过 10,000 行的分页、超宽结果、1 MiB 以上字段、标签切换和查询取消。

P0 的验收条件：对象定位不丢失连接上下文；结果查看模式切换不产生额外数据库请求；编辑失败可恢复；表大小缺失时不显示错误占位；刷新、切换标签和取消查询后不出现旧结果覆盖新结果的情况。

### 10.3 P1：SQL 分析与安全协作

目标是把“知道查询为什么慢”和“知道结构变更会做什么”做成可复核的工作流，建议在 P0 稳定后用 2 至 4 个迭代完成。

1. **结构化执行计划**

   - 统一 `EXPLAIN` 的原始文本、表格和树形节点模型，按 MySQL/PostgreSQL 能力分别解析，不把一个数据库的字段名称硬套到另一个数据库。
   - 计划页显示节点类型、访问方式、估算行数、成本、实际耗时和警告；原始计划可复制，解析失败仍保留数据库原文。
   - 后续再评估图形和火焰图视图；`EXPLAIN ANALYZE` 可能实际执行 SQL，必须在执行前明确提示，并遵守生产连接只读策略。

2. **Schema 对比与迁移增强**

   - 在现有列、索引、外键、生成列、Identity、迁移预览和审批记录基础上，增加重命名候选、依赖顺序可视化、破坏性操作分组和脚本逐段确认。
   - 对比页明确源连接、目标连接、Schema、表和元数据读取时间；脚本变化后重新计算指纹，旧确认记录不能用于新脚本。
   - 继续保持生产目标只读、SQL 可预览/复制/保存、执行必须显式确认；PostgreSQL 与 MySQL 的事务差异在界面上分别说明。

3. **查询结果差异比较**

   - 在现有稳定键和单元格定位基础上增加“仅显示新增/删除/修改”、差异数量、空值与类型变化说明，以及按行/列跳转。
   - 允许用户明确选择稳定键和比较范围；没有可靠键时只显示整行新增/删除，不自动猜测行对应关系。
   - 比较结果支持复制和有界导出，导出内容包含连接、Schema、查询摘要、执行时间和结果是否被截断。

4. **连接上下文和方言能力**

   - 连接复制、查询标签、对象编辑器、补全和执行计划都显示驱动类型及目标环境，避免把同名表误操作到另一条连接。
   - 将分页、排序、事务、执行计划、编辑和结构迁移能力改为显式驱动能力声明；不支持的动作显示原因，不渲染一个点击后必然失败的按钮。

P1 的验收条件：执行计划解析失败时仍能复制原文；结构迁移在脚本变化后必须重新确认；差异比较不会伪造行匹配；不支持某项能力的驱动会得到明确提示；所有涉及窗口布局的改动都有真实 Windows 窗口截图或明确记录无法执行截图的原因。

### 10.4 P2：数据库工作流与大数据量性能

这些工作建立在 P0/P1 的状态模型稳定之后，不提前引入大范围的产品表面。

- **查询管理**：按连接、Schema、时间、耗时和执行状态过滤历史；显示取消、失败和结果释放原因；保留本地日志，不上传 SQL 和凭据。
- **导入导出与复制**：支持选中行/当前页/查询结果的导入导出，先覆盖 CSV、JSON 和 SQL 三种稳定格式，再按驱动增加数据库专用格式；大结果采用流式处理和进度/取消。
- **导航树性能**：表数量达到 1,000 级别时仍采用虚拟列表、异步元数据批量读取和按需展开；表大小统计失败不影响 Schema 展开。
- **结果集性能**：继续限制可渲染行数和字段预览长度；对排序、筛选、比较和导出分别设置取消令牌、内存预算和结果代次检查。
- **多数据库体验**：MySQL/PostgreSQL 先保持 SQL 工作流一致但方言实现分离；MongoDB 和 Redis 使用各自的文档/Key-Value 操作，不为了统一界面而伪造 SQL 能力。

### 10.5 建议交付顺序

每个条目从最新 `origin/main` 建立独立分支，完成目标测试和真实窗口验证后立即提交、推送并发起 PR。当前开发线只用于承载正在进行的 Datagrip-like 集成工作，后续建议拆成以下小 PR：

| 顺序 | 建议分支 | 交付内容 | 主要验收证据 |
|---|---|---|---|
| 1 | `codex/feat/result-editor-workspace` | 结果查看模式、大字段查看、复制格式和编辑失败恢复 | `cargo test -p ramag-tool-dbclient --lib`、宽结果/大字段窗口检查 |
| 2 | `codex/feat/database-object-navigation` | 表树过滤、收藏、对象定位、表大小状态刷新 | MySQL/PostgreSQL 元数据测试、1,000 表导航窗口检查 |
| 3 | `codex/feat/structured-query-plan` | 原始/表格/树形执行计划和方言能力声明 | 驱动单元测试、计划解析失败回退、真实窗口检查 |
| 4 | `codex/feat/schema-migration-review` | 依赖顺序、重命名候选、脚本指纹和逐段复核 | Schema 对比测试、MySQL/PostgreSQL 回放、生产只读检查 |
| 5 | `codex/feat/query-manager-export` | 查询管理、流式导出和有界取消 | 大结果集测试、取消/内存预算测试、导出文件校验 |

每个 PR 至少包含 `cargo fmt-check`、目标 crate 测试、`cargo check-all`、`git diff --check` 和源码尺寸检查。涉及数据库真实行为时，补充 MySQL/PostgreSQL 集成环境；涉及 GPUI 布局、滚动、弹窗或交互时，使用 Windows computer-use 进行真实窗口检查，静态测试不能替代这项证据。

### 10.6 明确不做的事情

- 不把 Ramag 变成 DataGrip 或 DBeaver 的功能清单复制品；每个功能必须对应本地优先数据库工作流中的实际问题。
- 不为了显示统计而对每张表执行数据扫描，不把估算值伪装成真实表大小。
- 不把迁移 SQL 或大结果集默认自动执行/一次性加载；所有高风险动作都保留人工确认、取消和失败回读。
- 不在一个长期分支中积累所有数据库功能；每个独立能力使用可回滚、可审查的小提交。
